Banyak pengembang menganggap membuat indeks cukup dengan menulis `CREATE INDEX ON table(column)`. Di PostgreSQL, terdapat berbagai jenis struktur data indeks yang dirancang untuk tipe data dan pola query yang sangat spesifik.

---

## 1. Tipe Struktur Data Indeks di PostgreSQL

```mermaid
mindmap
  root((Tipe Indeks PostgreSQL))
    B-Tree (Default)
      Paling serbaguna
      Operator: =, <, <=, >, >=, BETWEEN, LIKE 'abc%'
      Struktur pohon biner berimbang O(log N)
    GIN (Generalized Inverted Index)
      Untuk data komposit / multi-elemen
      Pencarian dokumen JSONB, Array, dan Full-Text Search
      Mencari apakah teks/tag terdapat di dalam dokumen
    GiST (Generalized Search Tree)
      Untuk data geometri & spasial 2D/3D (PostGIS)
      Mencari radius lokasi terdekat (Nearest Neighbor), polygon overlap
    Hash Index
      Hanya untuk perbandingan kesamaan nilai persis (=)
      O(1) lookup sederhana
    BRIN (Block Range Index)
      Sangat hemat memori untuk data deret waktu besar (Time-series / Logs)
```

---

## 2. Aturan Emas Composite Index (Leftmost Prefix Rule)

Jika Anda membuat indeks gabungan (*Composite Index*) pada dua kolom:
```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

Indeks ini **BISA** digunakan untuk query:
- `WHERE user_id = 123 AND status = 'COMPLETED'` (Kedua kolom cocok)
- `WHERE user_id = 123` (Menggunakan *Leftmost Prefix* kolom pertama)

Namun indeks ini **TIDAK BISA** digunakan secara optimal untuk query:
- `WHERE status = 'COMPLETED'` (Karena kolom pertama `user_id` dilewati!)

---

## 3. Covering Index (Index Only Scan dengan Klausul `INCLUDE`)

Jika query Anda hanya meminta kolom `email` dan `full_name`, Anda dapat menyertakan `full_name` di dalam daun B-Tree tanpa menjadikannya kunci pengurutan:

```sql
CREATE UNIQUE INDEX idx_users_email_include_name ON users(email) INCLUDE (full_name);
```

Dengan teknik ini, PostgreSQL melakukan **Index Only Scan**: database mengambil seluruh data yang dibutuhkan langsung dari memori RAM Index **tanpa pernah menyentuh tabel utama di disk (*Heap Table*)**!

## 4. Praktik Interaktif: Eksplorasi Composite & Partial Indexes

Jalankan sandbox SQL di bawah ini untuk melihat pembuatan dan perbandingan indeks pada skenario e-commerce nyata:

CREATE INDEX idx_sales_region_status ON sales_transactions(region, status);

CREATE INDEX idx_sales_pending_urgent ON sales_transactions(customer_id, transaction_date)

<Callout type="tip" title="Over-Indexing Anti-Pattern">
  Jangan mengindeks setiap kolom di tabel! Setiap penambahan indeks menambah overhead penulisan (*Write Amplification*) saat operasi `INSERT`, `UPDATE`, dan `DELETE`. Pasang indeks hanya berdasarkan query aktual yang paling sering dieksekusi atau yang memiliki latensi lambat di log.
</Callout>
